## Repository architecture

Bowra Community packages a Python Lead orchestrator and authorized data/document tools plus specialist subagents, durable execution binding, scoped result artifacts, and optional intra-Turn collaboration. The Lead has a live provider-backed model loop. Collaboration is an explicitly admitted, identity-scoped exchange and waiting/resolve protocol; mere task messages do not grant work or access. An optional real Coach generates versioned Agent draft/test modifications from owner feedback, runs evaluation against the previous version and leaves authoritative release to the Agent owner/Team reviewer. This source preview is not a turnkey hosted instance and its example Developer API flow explicitly does not claim live CI success. [Community boundary](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/docs/agent-guide.md); [Lead](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/packages/bowhead_core/src/bowhead_core/agents/lead_orchestrator.py); [Coach](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/docs/help/agent-evaluation-with-coach.en-US.md).

## Operational model

An owner provides a scoped request; the Lead chooses domain tools or specialist help, then waits for evidence-bound results and may correct/return an incomplete delivery. The concrete inter-specialist dependency protocol is optional: unanswered questions and limitations cannot be treated as successful work. A legitimate initiating user can revise the running Lead work in a supported continuation mode. An Agent owner later evaluates and releases a changed Agent; this is prospective capability governance, not a grant of S5 authority. Neither a second answer-only evaluator nor Lead self-review is miscredited as S3*.

## S2 — Coordination

- State: C
- Function: Attenuate a concrete inconsistency between specialists depending on disputed evidence, blocking questions or overlapping task scope, with a bounded first-party coordination construct.
- Disturbance / variety regulated: Different independently assigned specialist executions may need the same source/result or disagree about responsibility and scope, causing premature or inconsistent completion.
- Decisive decision or feedback right: Resolve or waive a required dependency and authorize a corrected answer/scope through the existing task owner before the specialist resumes.
- Decision owner: A Lead or specialist can request, reply and revise via bound first-party agent_message path, but autonomous conflict-resolution judgement across multiple independent units is not established as a complete standing strategy.
- Supporting / enforcement mechanisms: Admitted responsibility cards, immutable execution IDs, authenticated artifact refs, ask/reply/update/resolve/wait ledger, durable checkpoint reauthorization.
- Closure path: Specialist conflict or missing prerequisite → ask task owner with provenance → authorized answer / blocked/waived limitation → waiting specialist resumes with revised scope or records limitation.
- Boundary reachability: First-party optional admitted collaboration is wired to live worker, ownership and same-Turn scope; unavailable conditions fall back rather than manufacturing completed coordination.
- Why this is / is not agent-owned: Specific dependency and task-boundary arbitration tools/feedback are exposed, not merely a generic mailbox; still requires configured discretionary arbitration ownership for full autonomous S2, so C not A.
- Distinct S1 units: Different specialist executions delegated from the ordinary Lead, each with exact execution IDs and separate assignments.
- Inter-S1 disturbance: A dependent specialist cannot satisfy an assigned task without a bounded answer or evidence from another assigned worker; inconsistent hand-off or waived blockers risk unsupported completion.
- Attenuating coordination relation: Admitted agent_message ask/answer/resolve with persisted owner and immutable reference checks; unresolved dependencies become explicit limitations rather than false success.
- Feedback into subsequent S1 behaviour: Specialist waits and then consumes the returned authorization/evidence or records refusal; subsequent work is changed by resolved dependency.
- Why this is S2-specific rather than generic communication / routing / sequencing / shared state / delegation: The code implements a required dependency resolution/waiver protocol tied to real assigned work and evidence, with return-to-waiter semantics rather than unvalidated messages.

## S4 — Outside-and-then intelligence

- State: P
- Function: Convert externally observed member/owner feedback and test evidence into prospective agent behavior/version improvements controlled by the legitimate Agent owner.
- Disturbance / variety regulated: User feedback reveals that an existing agent's instructions omit periods, misinterpret causal data or otherwise perform poorly on new work.
- Decisive decision or feedback right: Review Coach's proposed test and draft changes, accept required evidence and authorize future release of an improved Agent version.
- Decision owner: Agent owner or team reviewer in first-party owner-approved mode; Coach model suggests changes and tests, but cannot unilaterally publish an authoritative new release.
- Supporting / enforcement mechanisms: Coach question/point calibration, evidence-bounded working draft, before/after and held-out runs, candidate comparison, exact version/hashes, owner release checks and grants.
- Closure path: External feedback/observed failures → Coach develops a prospective option → versioned draft and model/evidence assessment → owner accepts/reviews → released agent version used on subsequent tasks.
- Boundary reachability: First-party Community Coach when available; owner workbench and local Developer API optional flags explicitly described. In unsupported deployments this mode is not claimed active.
- Why this is / is not agent-owned: Model-backed Coach proposes future adaptation, but the decisive launch into normal capability remains parent-owned and returns through explicit version release. Hence S4=P, not A.
- External distinction: Owner/member complaint about an actual task result, held-out failures and changes in business requirements relative to the agent's prior behavior.
- Future / prospective distinction: New prompt/tools/skills/tests target later Agent calls beyond fixing the single current answer.
- Adaptation option generated: Coach-generated saved Agent draft or bounded change proposal plus a revised suite/evaluation case and before/after comparison.
- Path back into current capability / S3: Approved released Agent version becomes available to subsequent ordinary project work, subject to the existing version/audience policy.
- Evidence: [Coach loop and held-out](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/docs/help/agent-evaluation-with-coach.en-US.md); [Coach authoring](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/packages/bowhead_core/src/bowhead_core/agent_coach.py); [owner gate](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/packages/bowhead_core/src/bowhead_core/agent_version_service.py); [release and review](https://github.com/Bowra/Bowra/blob/c6f444b112c57f686ef7d0b7a0c814663e667293/docs/help/permissions/publish-agent.en-US.md).
