## Repository architecture

BharatCode is a Goose-derived modular Rust coding agent; [README.md](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/README.md) defines local-first model selection and the source build. The operative [crates/bharatcode-core/src/agents/agent.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/agent.rs) `Agent` constructs provider/tool calls, enforces first-party tool inspectors, routes tool results and continues generated reasoning/work. The `developer` platform tools expose file, Git and command interaction; [crates/bharatcode-core/src/agents/platform_extensions/developer/delegate.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/developer/delegate.rs) implements independently instantiated subagents, while [crates/bharatcode-core/src/agents/platform_extensions/summon.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/summon.rs) supports async delegated sessions with task IDs and notification paths. Distinct subagents are operational S1 units, although their mere existence does not by itself establish S2 or S3.

There is a concrete whole-session management mode beyond generic delegation. [crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs) exposes `list_sessions`, `view_session`, `start_agent`, `send_message`, `interrupt_agent`. The list joins a shared `SessionManager` registry to `AgentManager` active/busy state, so the manager-model can inspect several current tasks, launch operational sessions, send control messages and cancel busy workers. A `send_message` call attempts `try_register_cancel_token` and rejects a concurrent instruction to an already-busy session, directing the caller to wait or interrupt. This is a source-backed per-destination interference attenuation constructor and a returned busy error, but *the collision rule* is deterministic, not independently model-owned. The controlling orchestrator model can nevertheless choose resource/work allocation and cancellations using its system-wide current view.

**Critical gate:** `orchestrator` is registered in [crates/bharatcode-core/src/agents/platform_extensions/mod.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/mod.rs) with `default_enabled: false`, `hidden: true`. It is not a default user-visible CLI feature. [crates/bharatcode-core/src/config/migrations.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/migrations.rs) preserves an explicitly stored enabled flag for platform extensions; [crates/bharatcode-core/src/config/extensions.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/extensions.rs) returns enabled extensions to the live runtime, while excluding hidden extensions from the *available-list UI*. The positive S2/S3 witnesses are therefore **only for an explicitly configured platform-extension mode**, not a default execution or an assertion of an observed multi-agent deployment.

The standalone [crates/bharatcode-cli/src/commands/review/handler.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-cli/src/commands/review/handler.rs) code-review command independently collects a real working-tree/raw Git diff and executes a separate headless `bharatcode run` for per-file correctness and separately discovered project check instructions. [crates/bharatcode-cli/src/commands/review/orchestrator.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-cli/src/commands/review/orchestrator.rs) caps worker concurrency, normalizes actual findings and emits them to the command user rather than to the producer's executing session. This supplies a first-party **complementary review constructor** with alternative artifact evidence and independent invocation, but not a proven S3* control/producer-correction closure: the human/developer must consume the report and arrange consequential return. The `C` state credits this primitive while withholding autonomous completed audit `A`.

A separate native [crates/bharatcode-core/src/security/adversary_inspector.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/security/adversary_inspector.rs) mode is enabled only when `adversary.md` exists; a new LLM inspection request compares the actual tool-call arguments and original user request against separate security rules and can block a suspect action. This inspects a different representation from the producing coder's claim, but is **pre-tool tactical safety gating**, fails open on reviewer failure, and by itself is not a returned whole-current operational audit. [crates/bharatcode-core/src/verify.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/verify.rs) optionally runs project checks upon task finalization (disabled by default) and yields a status notification; it is routine QA, not independent audit. Neither mechanism upgrades the code-review constructor to S3* A.

## Operational model

Default coding mode is a first-party model/tool S1 with safety, costs and privacy bounds. Opted-in `summon` and delegate modes produce separate S1 workers. The non-default platform orchestrator can oversee existing/new current sessions and autonomously decide launch/message/interrupt based on busy/status/conversation; a constructor-level per-session busy lock controls instruction contention. Independently launched raw-diff review subprocesses can collect corrective findings, but their output is directed to the external caller, without an automatic reviewer→current-manager→producer resumption path. The described functions are mode-bounded, not blanket claims that all are present in every installation.

## S1 — Operations

- State: A
- Function: execute requested coding, source research, edits and chosen tool actions in a model-directed closed agent/tool session; subordinate sessions can operate independently.
- Disturbance / variety regulated: uncertain user work, changing source state, command results, remote/local provider output, tool denial, task delegation errors and review feedback when supplied by a user.
- Decisive decision or feedback right: choose next file/tool/command, reason about its concrete result and finish or revise ongoing work.
- Decision owner: the first-party BharatCode agent model through `Agent`, subagent handler and platform tool registry; external inference backend has no inherited organizational right.
- Supporting / enforcement mechanisms: model API, platform extensions, session manager, tool inspectors, permission manager, retry, context/memory and local-first provider configuration.
- Closure path: user request → provider inference/model tool choice → inspected and permitted first-party tool execution → actual file/command/subagent observation → new model choice or terminal result.
- Boundary reachability: public `bharatcode` Rust CLI constructs `Agent` and platform developer tools; [crates/bharatcode-core/src/agents/agent.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/agent.rs) dispatches `tool_inspection_manager` then executes tool streams and resumes agent turns.
- Why this is / is not agent-owned: tool registry, permission and sandbox machinery alone cannot choose purposeful context-sensitive coding actions.
- Evidence: [crates/bharatcode-core/src/agents/agent.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/agent.rs); [crates/bharatcode-core/src/agents/platform_extensions/developer/mod.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/developer/mod.rs); [crates/bharatcode-core/src/agents/platform_extensions/developer/delegate.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/developer/delegate.rs); [crates/bharatcode-core/src/agents/platform_extensions/summon.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/summon.rs); [crates/bharatcode-cli/src/cli.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-cli/src/cli.rs).

- Confidence: high.

## S2 — Coordination

- State: C
- Function: attenuate instruction interference when independently operating sessions compete to direct one already-busy S1, using per-session exclusive cancellation registration and a returned conflict result.
- Disturbance / variety regulated: overlapped commands to a busy agent session and uncontrolled cancellation/instruction overlap across concurrent first-party operational sessions.
- Decisive decision or feedback right: `AgentManager.try_register_cancel_token` decides atomically whether a destination worker admits another parent request; a busy conflict is refused and the parent can wait or exercise separate interrupt.
- Decision owner: deterministic first-party per-session busy gate; the orchestrator-agent model chooses intended worker/next instruction, but the S2 *conflict-specific* admission is runtime-owned. Hence `C`, not `A`.
- Supporting / enforcement mechanisms: current-session registry, per-session cancellation tokens, busy/idle status, `list_sessions`/ `send_message`/ `interrupt_agent` tools.
- Closure path: a parent model selects a destination session → first-party `send_message` tries an exclusive busy registration → success allows one task execution, while busy denial is returned with wait/interrupt guidance → parent may select a different current worker, wait or cancel.
- Distinct S1 units: first-party independently executing BharatCode agent sessions managed by the platform; potential separate model parents can issue instructions to the same working destination session.
- Inter-S1 disturbance: overlapping current instructions and contest over destination session attention/execution while it is already busy.
- Attenuating coordination relation: explicit per-worker exclusive command admission/denial and returned busy state, distinct from simple status reporting or generic queue.
- Feedback into subsequent S1 behaviour: failed `send_message` returns an actual busy error to the orchestrating model, which can alter the targeted worker or request a permitted interruption before proceeding; the worker's current run is protected from a second overlapping message.
- Why this is S2-specific rather than generic communication / routing / sequencing / shared state / delegation: the busy test is an active *conflict* check on a shared operational worker rather than a mere forwarded task/message or UI status. It is narrower than file-level conflict arbitration.
- Boundary reachability: only in opt-in `orchestrator` extension mode; the registered and configured first-party session tools call `AgentManager` directly and do not require a third-party orchestrator. The extension is hidden/default-off, therefore no claim about default session operation.
- Why this is / is not agent-owned: the model owns current worker selection, but fixed busy/cancel registration implements conflict resolution. No autonomous S2 arbitration policy editing or independent regulator was established.
- Evidence: [crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs); [crates/bharatcode-core/src/agents/platform_extensions/mod.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/mod.rs); [crates/bharatcode-core/src/config/migrations.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/migrations.rs); [crates/bharatcode-core/src/config/extensions.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/extensions.rs); [crates/bharatcode-core/src/execution/manager.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/execution/manager.rs).
- Basis: structural.
- Confidence: medium, conditional on an enabled orchestrator.
- Caveats: this regulates competing instructions to one session, not all simultaneous file writes or a complete team workflow protocol.

## S3 — Inside-and-now control

- State: A
- Function: manage present, concurrently operative first-party agent sessions as an organization, choosing current work allocation, interventions and controlled interruptions with visibility of the whole current session set.
- Disturbance / variety regulated: several sessions with different task status, unavailable/busy workers, stalled work, mismatched assignments and ongoing results needing current corrective action.
- Decisive decision or feedback right: the orchestrator model can inspect loaded/busy/idle session roster and per-session output, start new worker, send a task/correction, inspect response and interrupt an existing worker to revise present obligations.
- Decision owner: model-guided first-party orchestrator session, not the deterministic registry or user permission alone.
- Supporting / enforcement mechanisms: `SessionManager`, `AgentManager`, `list_sessions`, `view_session`, `start_agent`, `send_message`, `interrupt_agent`, per-session busy/cancel tokens and inherited model configuration.
- Whole-system current view: `list_sessions` cross-references all known sessions with active/busy state and message-count/update time; `view_session` provides actual first/last message or separately summarized transcript, going beyond a single child tool response.
- Current-control decision scope: current team creation, choice of which session should do what next, dynamic intervention/cancellation, message correction and schedule of current worker attention; user remains owner of ultimate goals.
- Closure path: agent session state/response → orchestrator model's current system view → chosen `start_agent`/`send_message`/`interrupt_agent` → actual worker starts, changes action or stops → refreshed session status and response to manager.
- Boundary reachability: explicit opt-in through config migration/persisted enabled `orchestrator` extension; hidden/default-off does not mean borrowed external agent, but means this is **not a default-mode S3**. No human-only required decision at each management action is inferred from the source.
- Why this is / is not agent-owned: without the orchestrator's model choice the session manager can list and interrupt on command but has no autonomous priority/resource judgment over multiple sessions.
- Evidence: [crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/orchestrator.rs); [crates/bharatcode-core/src/agents/platform_extensions/mod.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/agents/platform_extensions/mod.rs); [crates/bharatcode-core/src/config/extensions.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/extensions.rs); [crates/bharatcode-core/src/config/migrations.rs](https://github.com/arbazkhan971/bharatcode-cli/blob/430e3047c705aa84762a8a46be4ff838cb159451/crates/bharatcode-core/src/config/migrations.rs).
- Basis: structural + explicit.
- Confidence: medium, opt-in only.
- Caveats: unlike an always-on management plane, this mode must be explicitly enabled and a model session must actively exercise the control tools; no actual live multi-session deployment trace was observed.

## S3* — Complementary audit

- State: C
- Function: provide a separately executed, raw-diff-based review/evidence-collection primitive able to challenge a producing coding run, without a built-in autonomous return to a current-control owner.
- Disturbance / variety regulated: generated-code defects, hidden diff-level regressions, security errors and missing tests that ordinary coding descriptions may underreport.
- Decisive decision or feedback right: first-party independent `review` subprocesses inspect real Git diff/files and emit categorized findings; the producing session does not select/approve them as part of its own current tool loop in that command mode.
- Decision owner: separate first-party reviewer agent subprocesses with own inference calls judge the raw diff; a human/developer needs to compose the findings→current-control→producer follow-up. Thus available audit constructor `C`, not a fully model-owned returned S3* `A`.
- Supporting / enforcement mechanisms: Git diff collection, scoped `.agents/checks/*.md`, `.agents/REVIEW.md`, per-file parallel main correctness pass, bounded check worker concurrency, report parsing/emission and command user consumption.
- Closure path: **partial only** — a separate invocation reads actual Git diff → model reviewers produce findings → CLI displays them to the user. Returning the result as a binding correction to the producer or opted-in S3 session is *not natively wired* in the `review` command. Composer must provide that path to claim operational S3* closure.
- Claim being audited: source changes actually made by a coding agent are correct/secure/testable.
- Ordinary reporting path: producer's model transcript/final response and its in-band test/tool status.
- Complementary access path: `bharatcode review` captures raw workspace Git diff and starts independent headless check/model subprocesses with separate prompts; not a rerun of the producing agent's self-summary.
- Who controls audit: external invoker starts a separate command; built-in reviewer-agent processes judge the diff. Output goes to invoker, not directly to a root manager.
- Independence boundary: separate process and independently executed model review of directly collected Git diff, rather than the producing agent's generated completion summary; the reviewer shares model/provider infrastructure and an externally invoked command, so does not establish organizationally independent always-on audit or a native automatic corrective return.
- Who acts on findings: the external developer/invoker receives the structured CLI findings and must explicitly route them into corrected production or an opted-in S3 controller; no first-party automatic action on findings is wired.

## Recursion

The default product has one coding S1. First-party `summon`/delegate can add independently working operational S1 sessions. In the source-configured opt-in `orchestrator` mode, per-worker busy admission supplies S2=C and the parent agent has a whole-current status/launch/message/interrupt interface it can autonomously use as S3=A. The hidden/default-off distinction is recorded; the repository does not imply all users run these controls. Standalone review subprocesses supply the alternative raw-artifact S3*=C constructor, not a permanently active audit authority. User/maintainer organization, external models and GitHub Action reviewer stay outside the scored recursion.

## Variety and escalation

The basic agent absorbs changing code/tool context. Multiple native S1 sessions create workload and instruction variety; hidden orchestrator mode can inspect current sessions, allocate work and intervene, while busy registration prevents overlapping demands for the same session. Raw-diff review provides alternative evidence about code changes but requires an external invoker to return findings into corrective current governance. Security reviewers and permissions gate unsafe actions without a proactive future strategy or legitimate highest policy decision. Memory, scheduling and INR budgeting constrain current work rather than closing S4/S5.

## Evidence gaps

This classification is source-static at a frozen public commit; no cargo/provider-backed end-to-end multi-session execution or model score is claimed. `orchestrator` is hidden and disabled by default yet the first-party configuration/migration model admits an explicitly enabled mode. The S2=C positive is narrowly **per-session overlapping instruction conflict**, not global file conflict arbitration. S3=A requires a model session to actively use the enabled roster and current-control tools; none is claimed by default. `bharatcode review` separate headless raw-diff subprocesses provide complementary access but there is **no installed automatic findings→current-S3→producer corrective loop**, so S3*=C and not A. These are bounded modes and conservative ownership at the chosen product boundary; external governance, hypothetically enabled future functions and maintainer PR CI do not substitute for missing loops.
