## Repository architecture

The public Workflow One canvas enables a user to connect input, model-backed agent, script, conditional/HTTP and output nodes as a directed acyclic graph. A local Express entry `server/server.js` wires model adapters, first-party tool executor and an Orchestrator. `server/orchestrator.js` schedules eligible agent nodes when predecessors finish and feeds their upstream content through `server/template.js`; the node can select an external `dsh` headless agent if installed and ready, otherwise falls back to a first-party built-in LLM tool loop. `server/plan-mode.js` optionally runs a *current-task* plan, execution and summary. The returned model output/artifacts/trace feed downstream deliverables; synchronous JS graph scheduling, missing-input and failure routing do not by themselves own independent management. ## Operational model

The graph author/operator owns workflow topology, input contracts, policy and per-node tools/roles. At execution, individual model-backed nodes choose their task-level action via configured model/tool feedback; deterministic runtime controls decide eligibility/concurrency/error propagation and surface outputs and diagnostics. A user may invoke AI to edit a canvas, but the model's authorization is bounded to a current tool session, and its changes are validated by first-party graph rules. No first-party whole-institution model governs a stable, separately viable S1 portfolio.

## Recursion

The meaningful positive unit is the model-driven operating agent *within* each composed DAG workflow. Workflow/user input and model/tool data introduce variety; each S1 agent can adapt current tool/answer decisions within its assigned node, while DAG conditions, retries, fixed concurrency/timeout and cancellation limit operational exposure. Node result events, SSE, traces, artifacts and Feishu notifications inform users of statuses, but these status indicators alone are neither independent organizational algedonic governance nor complementary S3* audit.
