## Repository architecture

`codemachine run <script>` calls a first-party parser and `CoordinationExecutor`; parallel groups run concurrent `executeAgent` calls and sequential groups stop on failure. `executeAgent` loads agent configuration, chooses an authenticated engine with fallback, constructs/merges MCP context, registers live process status, invokes `engine.run` with a complete prompt, streams output/telemetry/session IDs, and returns an output and optional chained prompts. Installed external engine CLI implementations supply the actual model/tool reasoning. The harness intentionally assembles a tool-enabled coding-agent operating loop, not merely links an inert model SDK. [CLI entry](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/cli/commands/run.command.ts#L16-L78); [per-task runner invocation](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/agents/runner/runner.ts#L196-L545).

Separately, `runWorkflow` loads a chosen template, filters selected tracks/conditions and runs optional pre-execution controller conversation, then step runners with resumption and user-selected or template-defined autonomous/interactive modes. A module may intentionally expose a directive file and `stepBack` loop to repeat previous workflow steps. These are meaningful workflow mechanisms; a positive S2 or S3 ownership mapping still requires an evidenced *specific* cross-S1 disturbance or whole-current management authority, not merely multi-agent naming, step sequencing, logs or a rewind instruction. [workflow entry/filtered steps](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/workflows/run.ts#L130-L260); [pre-execution controller handoff](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/workflows/controller/view.ts#L270-L405); [loop evaluator](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/workflows/directives/loop/evaluator.ts#L12-L66).

## Operational model

The S1 work cells are configured external-coding-CLI-backed agents invoked by CodeMachine with a goal/prompt and code workspace; they respond to tool results inside the external coding engine. CodeMachine owns agent selection, prompt composition, startup, context/session state, monitors and orchestration return. The operator/developer configures tasks/templates, scripted ordering, models, checkpoints and permissions. The first-party default includes an Ali model-backed workflow builder, and the runnable CLI supports arbitrary installed configured agents.

## S1 — Operations

- State: A
- Function: Execute discretionary coding/workflow instructions in a real workspace through configured model-backed coding agents and return their outputs.
- Disturbance / variety regulated: Changing codebase state and task intent, tool errors, provider availability, multi-step coding goals and responses from the workspace.
- Decisive decision or feedback right: The invoked coding-engine agent interprets the current task, chooses modifications/tool steps inside its own engine loop and responds to observations; CodeMachine's runtime launches and resumes that specific actor through a first-party installed command path.
- Decision owner: Installed model-backed coding-work cells connected by CodeMachine runner; the cognition and inner tool loop are external-provider machinery, while first-party CodeMachine owns their task issuance, runtime integration and result/session return. Provider internals are not silently credited as first-party metasystems.
- Supporting / enforcement mechanisms: Agent templates, combined prompts, engine registry/auth cache/fallback, MCP tool context, abort/timeout, monitoring IDs, JSON event/status store, chained prompts, process stdout/session callbacks.
- Closure path: CLI or TUI goal → first-party coordinator/step loader → `executeAgent` and external `engine.run` → model-backed tool/observation loop → output/status/session record → result or subsequent chained workflow step.
- Boundary reachability: `registerRunCommand` calls `CoordinatorService.execute`; its executor directly calls `executeAgent`, which resolves and calls a real configured engine; the shipped workflow runner independently uses the same method. This is not only an abstract interface or test fixture.
- Why this is / is not agent-owned: If model-backed coding engines are removed, authentication checks, parser, prompt files, static workflow gates and logs remain, but no autonomous coding decisions or tool-mediated progress. Their internal intelligence is a dependency, yet the assembled first-party agent-operating mode is real.
- Evidence: [runnable CLI](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/cli/commands/run.command.ts#L16-L78); [execution groups](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/agents/coordinator/execution.ts#L35-L181); [engine selection, run and result](https://github.com/moazbuilds/CodeMachine-CLI/blob/572def63eb808e95b18ccf6c69a13d7a13fe06fd/src/agents/runner/runner.ts#L196-L545).
- Basis: Structural deployed standard CLI/TUI path, assuming a supported coding CLI is configured.
- Confidence: High for integration of the real agent executable; no source-independent performance assertion.
- Caveats: Vendor model/tool loops and authorization are external; no live model execution was used in this assessment.

## Distributed OSS parent arrangement

The public GitHub contributor project and the user's individual local CodeMachine installations do not form one evidenced shared operational control recursion. ## Self-hosted and non-human modes

Scripted `codemachine run` and enabled workflow autonomous mode can execute without per-step human input after user setup. A configured controller may be explicitly human-interactive before switching to execution, and optional checkpoints provide another local gate. Neither establishes a separate parent S3/S4/S5 mode without function-specific authority and return evidence.

## Recursion

Agent IDs, child process hierarchy and separate engines describe delegated operational work cells. An Ali-generated workflow or MCP subagent can have its own tools, but no automatically recursive viable S2–S5 structure follows. At a different project recursion, a custom workflow could implement management; this assessment does not assume it exists by default.

## Variety and escalation

User goals and workspace changes produce operational variety; template prompts/engine fallback attenuate invocation difficulty while delegated coding engine actors absorb discretionary task variety. Sequential stop, directive `loop`, checkpoint and status monitoring alter session flow. Those are task-level control/enforcement until an organizational conflict, manager right or identity-authority return is concretely evidenced.
