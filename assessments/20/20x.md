## Repository architecture

The desktop uses an agent adapter to run task-specific model sessions with repository, MCP tools, skills and transcripts. Triage compares task similarity, agent fit and live subscription quota, then writes assignment/priority/skills/repository. Mastermind has full task and workload views and state-changing tools. Sibling tasks exchange status and outputs, but no specific incompatible-source conflict repair circuit is demonstrated. An optional independent heartbeat model checks current external PR/CI/issue state; actionable findings return to the original task agent under an authority gate. Sources: https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/main/agent-manager.ts, https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/main/mcp-servers/task-management-core.ts, https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/main/heartbeat-scheduler.ts.

## Operational model

A task model decides actual code changes and validates results. An on-demand current-portfolio model can choose/revise task assignments based on global workload, but the user retains consequential action control. Later heartbeat monitoring independently reads changed external reality and returns bounded findings. Task decomposition does not itself establish cross-S1 conflict regulation; retrospective skill learning does not establish prospective S4.

## S3* — Complementary audit

- State: A
- Function: challenge task ready-for-review claims against later real PR, CI and linked-issue state.
- Disturbance / variety regulated: new requested changes, failing CI or external issue drift after the task agent's last report.
- Decisive decision or feedback right: separate heartbeat model decides whether new external findings are actionable.
- Decision owner: fresh heartbeat-specific model session, distinct from original task implementer session.
- Supporting / enforcement mechanisms: heartbeat.md, deterministic gh preflight, periodic timer, dedupe and authorization gate.
- Closure path: task status/checklist → current external checks → model diagnoses drift → findings forwarded to task agent or to human for authorization.
- Why this is / is not agent-owned: a model interprets changed real-world state and requests correction; preflight and forwarding are deterministic controls.
- Evidence: https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/main/heartbeat-scheduler.ts and https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/main/agent-manager.ts and https://github.com/peakflo/20x/blob/168693be23965f2e5cc8f15c32093544234c6d01/src/shared/system-authority.ts

- Confidence: medium-high when opt-in monitoring is active.
- Caveats: heartbeat requires a useful checklist and enabled task; this is no independent auditor organization.
- Claim being audited: task agent's ready-for-review state implies no unresolved relevant linked PR/CI/issue updates.
- Ordinary reporting path: task agent transcript, completion result and status.

- Who acts on findings: task agent receives authorized corrective input; privileged actions are escalated to the human.

## Distributed OSS parent arrangement

## Self-hosted and non-human modes

The local-first app can use many external providers; this does not multiply autonomous owners. Mastermind allocation is a selected model-backed current task-management mode; heartbeat auditing requires a configured checklist and an actual later model session.

## Recursion

Independent task or subtask sessions may have durable contribution and local environment, but are not automatically complete viable systems. A parent prompt that merely sees sibling status is not proven S2.

## Variety and escalation

Provider quota, skills and task statuses feed current model allocation. A changed PR/CI issue enters the heartbeat complement, then authorized findings return to task execution. Privileged operations stay gated for humans, without automatically assigning S5.
