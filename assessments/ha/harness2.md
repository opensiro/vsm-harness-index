## Repository architecture

`harness2/core/schedule.py` constructs benchmark/executor/mode-specific, seed-scoped namespaces, orders tasks within domains, reads the base harness and obtains real base rollouts through an adapter. `run_task` calls `_run_one_mode`, which invokes `recursion.run_mode` and builds a candidate selection pool. The task loop executes actual proposed harness modifications using the selected substrate; `_run_stage` invokes `Proposer.call` for *workspace edits*, extracts the returned component tree, validates the editable surface, allows one failed patch revision and falls back to previous tree on failure. `_roll_many` probes candidate trees by running them on the **same task**. These are executable first-party effects, not only prompts/paper descriptions. [harness2/core/schedule.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/schedule.py#L480), [harness2/core/schedule.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/schedule.py#L566), [harness2/core/recursion.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py#L108), [harness2/core/recursion.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py#L135), [harness2/core/recursion.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py#L260), [harness2/core/recursion.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py#L303), [harness2/core/proposer.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/proposer.py#L126), [harness2/core/tree.py](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/tree.py#L1).

Parallel recursion creates independent general/domain candidates and then composition candidates from observed execution contrasts; sequential recursion carries a refined tree and earlier evidence into subsequent cycles on the same task. The standard path thus models an agent's action decisions *about harness design* plus real probe results, without asserting that Harness² owns the external executor's internal tool-use decisions. A second, separate **cross-task** return path is explicitly shipped. For each domain, `run_domain` maintains `Library` stores across task order; `_run_one_mode` passes the prior library into the proposal context and after a successful chosen task calls `reflect_adoption`. The reflector invokes a model-backed proposer on chosen harness, candidate contrasts, decision notes and deliverables to distill an experience record. `Library.add` saves **the adopted harness tree**, reasoning and lessons, and regenerates `INDEX.md`; `context.build` makes that directory available to the next proposal. Subsequent within-domain tasks therefore receive actual selected and persisted cross-task strategy material, not merely a disconnected evaluation report. A model can autonomously choose/describe the adopted option in supported configured mode, and persisted accepted knowledge returns to future agent-harness design action. ## Operational model

In the chosen **harness-improvement system** recursion, executing/probing/editing a candidate harness on current task feedback is S1 operational work. Distinct from that, harvesting accepted cross-task domain experience and returning it to later candidate design is a prospective S4 capability-learning feedback organ. This does **not** imply S4 ownership in the uninspected separate deployed target agent. There is no default multi-division operational interference regulator, whole-current organizational S3 manager, independently corrective S3* channel or ultimate S5 purpose arbiter in the inspected distribution.

## S1 — Operations

- State: A
- Function: Carry out the present task's harness-editing and probing work through autonomous model-chosen candidate changes, actual executor rollouts and evidence-informed candidate selection.
- Disturbance / variety regulated: Unseen tasks, insufficient baseline harness behavior, different candidate tool/prompt/skill modifications, executable errors and heterogeneous task deliverables.
- Decisive decision or feedback right: The configured proposer model chooses what edits to write inside the allowed harness tree; selector model chooses among concrete completed candidate outputs using execution evidence. Those chosen changes are validated and run by the shipped orchestration, with later candidate/edit choices exposed to resulting observations.
- Decision owner: Model-backed Proposer/selector operating through first-party `_run_stage`, `run_mode` and `run_selection`; external model/runtime implementations supply inference and task execution but do not replace first-party decision/feedback routing.
- Supporting / enforcement mechanisms: Python stage scheduler, editable tree validation, candidate/run budget ledger, real adapter execution, retry/fallback, evidence-safe render, filesystem result records and selection persistence.
- Closure path: Task/base rollout → proposal-agent harness edit → first-party tree accept/reject → substrate probe with new tree → observed deliverable/trajectory → independent composition/selection decision → chosen current-task output and selection record.
- Boundary reachability: Public CLI `run_sweep` → `run_domain` → `run_task` → `run_mode` → `_run_stage`/real candidate adapter execution → `run_selection` is shipped source. Proposer and selector may be model-backed via released `Proposer.call` implementations rather than sample-only DemoProposer. No external task executor cognitive function is claimed as a Harness² internal actor.
- Why this is / is not agent-owned: First-party code gives model-backed editor/selector discretion that changes candidate harnesses and selects from observed task outcomes; deterministic scheduler, validator and external benchmark judge are only enforcement/evidence mechanisms.

## S4 — Outside-and-then intelligence

- State: A
- Function: Learn from current encountered environments and adopted task-level harness modifications to autonomously maintain a reusable future-facing improvement library that influences subsequent harness-design decisions across new tasks.
- Disturbance / variety regulated: Open-world tasks arrive that were not known at initial harness construction; improvements for one problem may not transfer directly. Cross-task domain patterns, changing successful component choices and observed errors must inform future harness proposals.
- Decisive decision or feedback right: After actual current-task rollouts, the model-backed selector picks an adopted harness from candidate evidence and model-backed `reflect_adoption` distills transferable experience. First-party `Library.add` accepts that model-selected result/lesson into durable per-domain library, and subsequent proposer/editor sessions read it for future harness reconfiguration.
- Decision owner: Configured autonomous selector + experience-reflecting model agent inside the shipped run_task/run_domain loop. Deterministic file/library code persists and presents the agent's chosen strategic material, not an external human deciding each adopted lesson.
- Supporting / enforcement mechanisms: Domain task stream, mode-separated Library, selected harness tree and adoption metadata, contrastive trajectory record, `EXPERIENCE.md` and `INDEX.md`, context injection, safe tree validation, leak prevention and retaining only earlier tasks.
- Closure path: Environment/task rollouts → model selection of accepted harness → model distills evidence-supported transferable future lesson → library persists full adopted harness + rationale → next task imports library into new model proposer context → its operational harness edits can change under accumulated past experience.
- Boundary reachability: A first-party public `run_sweep` invokes `run_domain`, creates `Library` objects per mode/domain and executes tasks sequentially. `_run_one_mode` calls `reflect_adoption` and, with evidence-rich experience, `mode_lib.add`; `_run_stage` passes `library_dir` to `context.build` which actually copies old library context into the next proposer session. No bespoke adopter glue is needed for this supported released mode.
- External distinction: Novel tasks in the same domain arrive after prior harnesses have been accepted; actual task-execution contrasts, error patterns and domain-specific cues are fed back through the prior-task experience library rather than assumed from static program configuration.
- Future / prospective distinction: The reflector distils a transferable cue/lesson intended for **later unknown tasks**, and Library stores adopted trees and why they were chosen; this is not the immediate selected deliverable alone.
- Adaptation option generated: An autonomous proposer/editor generates new harness-component edits based on stored prior domain experience, and an autonomous selector/reflection loop chooses, explains and retains the successful candidate tree and lesson to inform later alternative edits.
- Path back into current capability / S3: `Library.add` persists the chosen tree and lesson, `context.build` copies the resulting library into the **next** proposer work directory, and `recursion._run_stage` hands it to the model edit session whose validated candidate modifies the next task's executable harness. There is no separate whole-current S3 manager, so the concrete return is direct into next S1 harness-improvement capability at this recursion.
- Why this is / is not agent-owned: The agent makes substantive adoption and transferable-experience decisions from observed external task outcomes; first-party memory storage/return closes them into future edit decisions. This is a prospective reusable *improvement-harness capability*, distinct from current task's best-output selection alone.

- Disturbance / variety regulated: User-selected benchmark, base model, allowed editable components, executor, task scope and no-leak policies bound optimization but do not entail an identity/purpose governance dispute.
- Decisive decision or feedback right: CLI/research operator fixes the task stream, model/substrate budget and source boundaries; validators enforce prechosen component constraints. ## Distributed OSS parent arrangement

Google Research authors, external model provider, target OpenCode/Codex executor, human experiment owner and the Harness² improvement agent are distinct decision holders. The external operator supplies task source/configuration and may own legitimate institutional aims, but the repository does not expose a closed S5 or present whole-organization S3 owner. Model-backed selector/reflector does own bounded S4 adaptation in its *improvement process* mode; no unsupported parent-mode `(P)` is claimed merely because humans can configure tasks or launch experiments.

## Self-hosted and non-human modes

The source supports local `harness2-demo` without model credentials and configured CLI/benchmark modes using external models and task executors. The latter modes can revise and probe harness components, perform evidence-backed selection and write a domain library for later tasks. Live APIs, unrestricted model-executor network and disabled Codex sandbox require operator diligence; frozen primary source review here did not execute a model run, incur provider cost or access public grading criteria.

## Recursion

The assessed system is the continual harness-improvement organization, not the downstream agent's internal organization. Within it, task-level improvement is operational S1; cross-task learning and selected future design knowledge can close S4. Neither multiple proposal stages nor independent benchmark domains create separate viable S1 organizations with default S2/S3/S3*/S5. The observed adaptive features of a future deployed model application would require its own assessment, not inheritance.

## Variety and escalation

Candidate-tree constraints, sandbox adapter restrictions (when configured), evidence no-leak filters, stage retry/fallback, budget ledger and per-domain library retention bound variation or avoid invalid changes. Agent-generated candidate comparisons and model reflection supply feedback on useful harness redesign. Those technical guards do not imply a separate systemic audit or identity policy organ.

## Evidence gaps

- Both task-level editor and cross-task selector/reflector are *source-wired* autonomous modes when configured with a model provider. `DemoProposer` is deterministic; source review here does not substitute it for agent autonomy. No external model-backed end-to-end benchmarks executed.
- The code explicitly stores previous selected harness *trees* and reflections but reinitializes each new task with a base harness; prior library **informs** future edits rather than auto-installing a complete accepted tree as the new task's execution starting state. Positive S4 is narrowly about this autonomous **prospective improvement-library feedback**, not about guaranteed replacement of the target agent's operating configuration.
- Only one task-output judge/selection channel is evidenced. `judge_one` is a post-run benchmark scorer separate from editing, not an independently corrective S3* body with whole-current control obligations. The independent-source audit and closed S3 route are absent at this recursion.
- Potential benchmark contamination/network safety is a source warning; no unsafe public grading access, external Codex or cloud model calls, user credential use or full benchmark test runs were performed. Library transfer efficacy and model result quality are not claimed.
