## Purpose

Revalidate the canonical cohort under VSM Harness Methodology `0.3.1`, with particular attention to the ownership-mode boundary introduced in `0.3.0` and clarified in `0.3.1`:

```text
S1   P not published
S2   P not published
S3   P / A(P) / C(P) allowed as supervisory/current-control exception
S3*  P not published in the 0.3.x line
S4   P / A(P) / C(P) allowed as parent-assisted adaptation exception
S5   P / A(P) / C(P) allowed; canonical parent-governed case
```

This is a Methodology publication boundary for autonomous agent-harness assessment, not an ontological claim that humans cannot own other VSM rights in broader organizations.

## Relationship to R1

R1 remains immutable historical evidence for the two checks already recorded under Profile `0.2.0` / Methodology `0.2.1`.

Once R2 begins, do **not** append new R1 checks or move canonical current provenance backwards to the older R1 semantic pair. The unfinished R1 scope is not converted into synthetic `blocked` outcomes. R2 takes over future canonical reassessment work using a fresh scope snapshot and the current `0.2.1 / 0.3.1` contract.

Existing R1 rows in `data/reassessment-history.psv` remain append-only history and must not be rewritten.

## Review strategy

R2 is evidence-driven and repository-relative. Do not mechanically transform old vectors.

For each harness:

1. read the current canonical assessment and its accepted `review_ref`;
2. inspect upstream changes since the newest successfully checked boundary first;
3. determine whether upstream change requires a new-ref reassessment or whether a same-boundary semantic revalidation is sufficient;
4. re-establish S3, S4, and S5 functions before classifying ownership;
5. identify the decisive organizational decision/feedback right in every first-party mode claimed;
6. separate agent, deterministic runtime, developer/configuration, human, parent-system, and distributed-arrangement ownership;
7. establish the return/closure path for every positive parent mode;
8. inspect self-hosted/operator/supervised modes only when they are first-party and materially alter ownership;
9. preserve plain `A` for intentionally non-human organizations when no qualifying parent mode is established;
10. use `?` rather than infer `(P)` from incomplete evidence.

A full repository re-proof is required only where upstream delta, new ownership-mode semantics, or weak existing evidence makes the current assessment insufficient.

## Parent-mode evidence threshold

Do **not** infer `P`, `A(P)`, or `C(P)` from any of these alone:

- self-hosting;
- human presence;
- approval hooks;
- stop/kill buttons;
- merge review;
- maintainers or contributors;
- dashboards/operator UIs;
- generic configuration or extension points;
- issues, roadmaps, or backlogs.

For S3, the parent path must close a real whole-system current-control decision. For S4, it must close a real outside-and-then adaptation judgment. For S5, it must close identity / ultimate-policy authority and return that decision into operation.

## Priority order

Review higher semantic-impact cases first:

1. current S5 `P` assessments, because `P` is now explicitly an ownership mode rather than an S5-only special symbol;
2. harnesses with S3 or S4 `A`/`C` plus documented self-hosted, operator, approval, or supervision modes that may or may not qualify for `(P)`;
3. distributed OSS harnesses where contributor-local private execution context may leave legitimate S3/S4 decisions with a parent arrangement;
4. intentionally non-human/swarm-like organizations where plain `A` should remain plain `A` unless a distinct first-party parent mode is actually established;
5. remaining canonical assessments via a targeted `0.3.1` compatibility check.

## Batch execution

Operational batches should normally contain at most five harnesses.

Each batch must:

- use only harnesses in the frozen R2 scope;
- pin the exact upstream state inspected;
- return one explicit R2 outcome per harness;
- update canonical assessment provenance/freshness only after successful review;
- append the matching event to `data/reassessment-history.psv`;
- regenerate affected signatures/TLDR/rankings when a canonical vector or cohort-relative signature changes;
- pass repository validation and Methodology `0.3.1` regression tests before merge.

## Provenance rules

Every successful R2 check records current semantic provenance:

```yaml
profile_version: 0.2.1
assessment_procedure_version: 0.3.1
last_checked_ref: <newest upstream ref successfully inspected>
last_checked_at: 2026-09-16
last_reassessment_round: R2
```

`generated_profile_version` and `generated_assessment_procedure_version` are immutable artifact-origin metadata and must not be changed.

`assessment_changed_at` advances only when the canonical assessment materially changes. A semantic revalidation that confirms the existing assessment may advance current provenance and freshness while leaving `review_ref`, `reviewed_at`, and `assessment_changed_at` unchanged.

## Outcomes

Use exactly one of:

- `no-upstream-change`
- `no-material-change`
- `reassessed-unchanged`
- `reassessed-changed`
- `same-ref-correction`
- `blocked`

`blocked` does not advance canonical freshness/current provenance.
